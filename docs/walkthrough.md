# 运行示例

以下是当前实现的文字模拟，不是在真实项目中执行初始化、开发或发布。
假设 Skill 已安装，本地 Codex 与 Cursor 能访问同一个记录中心。
示例项目为 `D:\work\member-app`，记录中心为 `D:\work\records-data`；
这些路径仅供说明，不是程序默认值。

## 1. 首次在 Codex 中使用

用户说：“用 biz-project 管理这个项目，然后修复优惠券使用流程。”

Codex 先读取 Skill，运行只读检查，发现尚无项目登记。它先检查当前全局
指导和接入意愿。本例用户已明确说“用 biz-project 管理这个项目”，属于加入授权。
如果只是调用 Skill 或要求普通开发，则先问“是否将这个项目加入统一记录？”；
没有回答时不生成记录。如果选择“不加入”，只在本机共享配置中保存拒绝，
不改项目或中心；以后换聊天或切到 Cursor/generic 也跳过，不反复询问。
仅明确说“重新加入这个项目”时才恢复。

确认加入后才处理记录中心配置：找到已有 `biz-project` 中心就复用；发现多个候选中心
就询问使用者选择，不在每个项目中分别创建中心。没有中心时，先问：
“统一记录中心希望放在哪里？目录应位于 Skill 工程和业务项目之外。”
此时不创建任何目录、配置或项目调用区块，也不会用建议位置代替确认。

用户回复：“放在 `D:\work\records-data`。”Codex 收到这个明确路径后，
才以 `--join-confirmed --records-root "D:\work\records-data"` 初始化。若只说“继续”，则
还没有确认存放位置，Agent 应继续询问。Skill 工程目录始终不存放私人记录。

如果检查只发现旧 `project-records` 配置或中心，Codex 先报告候选位置并
询问要沿用还是另选，不自行复用、改名、迁移或删除旧中心。

确认首次接入后，初始化为项目分配稳定 ID，在中心创建项目配置和概览，
并向项目实际生效的 AGENTS 文件添加一个调用区块。原有分支、发布、埋点、
授权和文档规则全部保留，原有代码也不因初始化而修改。

随后 Codex 从原有规则中补齐项目配置。脚本只创建空配置，不能自行推断
哪个分支是发布分支，也不会宣布已有旧文档完成迁移。若旧规则仍要求
维护本地文档，Agent 必须继续遵守，直至用户授权调整或迁移。

## 2. 开始开发一个功能

Codex 先查是否已有同范围的功能记录。新功能才创建记录，例如
`coupon-flow-fix`，并确定汇总负责人。主文档记录需求、范围、关键决策和
分工；开发检查点记录实际改动、验证结果、风险和后续事项。

例如当前证据是：“实现已完成；自动测试通过；尚未人工验收；未合入
发布分支。”记录必须保留这些区别，不能把“写完代码”记成“已上线”。
脚本创建的功能状态最初是 planned；后续状态由负责人核对证据后维护。

## 3. 换到 Cursor 继续同一个功能

用户在 Cursor 中说：“继续处理 coupon-flow-fix，先读取项目记录。”

Cursor 使用 `--host cursor` 检查，发现项目配置已经存在，但本工具入口
尚未安装。初始化只新增 `.cursor/rules/biz-project.mdc`，作为常驻
调用指导。项目 ID、功能 ID、Codex 规则和既有记录都不变。

Cursor 读取同一份功能主文档和进展，知道当前还有人工验收未完成，
从这一点接续工作。它不依赖 Codex 聊天历史，也不会声称能看到那段聊天。
它仍需核对实际代码、当前分支和工作区；记录中的历史结论不是实时事实。

## 4. 多个 Agent 分别提交结果

若用户已授权协作，Cursor 的执行 Agent 和 Codex 的检查 Agent 可以分别
写独立进展。例如一个报告实现结果，一个报告验证结果，各自有稳定的
检查点 ID。脚本将它们发布为不同文件，不向同一个共享日志并发追加。

负责人读取这些结果、核对证据，再汇总主文档。有冲突就记录冲突及其
处理结果，不能让后提交者覆盖先提交者。重复提交相同检查点和内容不会
新增一份；同一检查点被提交成不同内容时会被拒绝。

这不是自动调度。Skill 不会自行创建其他 Agent、给另一个工具发消息，
也不通过作者标签强制权限。主文档仍依靠约定的单一负责人维护。

## 5. 合并或发布

用户授权合并后，Agent 先核对源分支相对目标分支的内容、未提交改动和
项目自己的确认要求，再执行授权范围内的操作。记录保留源提交、目标
提交、验证结果、观察时间，以及本地和远程核对的区别。

如果项目规定“合入开发分支不算发布”，这时只能记为已集成、未上线。
如果项目规定“合入发布分支即上线”，则按当次 Git 证据更新发布状态，
同时维护该项目要求的概览或本地文档。没有授权，不因 Skill 提示而
自行合并、推送或部署。

## 6. 下次新聊天或另一个项目

新聊天重新检查规则和记录，再从功能 ID 继续，不为每次聊天另开一份
重复功能文档。另一个未登记项目须先询问是否加入；同意后复用同一个中心，登记独立项目 ID，并
保留自己的分支、验证和发布约定。

将来日周记产品可读取这些统一格式的项目、功能和进展数据。
当前没有该接入，也没有跨机器同步或远程 Agent 数据分发。
